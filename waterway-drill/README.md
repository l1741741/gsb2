# 水道演练 · Waterway Drill

一个原创的回合制浏览器水道调度演练。玩家在有限回合内先布置若干闸门，再一次性确认结算，
把水送到指定池子，同时避免淹掉低处的检修格。素材全部是 Canvas 2D 几何图形，
没有任何第三方运行时依赖，也不需要随机生成即可通关。

本目录是从 `renderer/` 之外新增的独立工具；仓库中原有的 `renderer/` 示例保持原样、未被改动。

## 玩法速览

- 地图上有池子、闸门和有容量上限的分叉支路，每条边旁直接标出本回合实际通过的水量。
- 每个池子的水位与容量直接画在地图上（如 `12/12`）；右上角是当前回合与剩余回合。
- 选择/取消闸门只会改“待确认布置”；按「确认结算」才会把这批布置一起结算成整回合。
- 结算后可「撤回一步」，恢复到该回合开始前的水位与闸门状态，改走另一种安排。
- 「导出记录 / 导入记录」可以离线保存走法；导入时先用当前关卡完整复核，不合规的记录会被明确拒绝。

## 结算规则（为什么结果与文件顺序无关）

水量一律以整数“格”计，结算只用整数加减，因此逐格可对账、重放无浮点漂移。

1. **出流按回合开始时的水规划。** 某池本回合可放出的水 = `start + 外部来水`，
   与同回合后来才抵达的水无关，所以水沿支路走一跳至少需要一回合。
2. **分叉按最大余数法分配。** 某池多条出水支路按容量比例分配可放水量；容量不够时
   各边分到的量之和恰好等于可放水量，余数并列时按支路 id 升序补齐。
3. **应用按高程从高到低、同高程按 id 升序。** 支路只允许从高池流向低池；
   溢流只能倒向更低高程的池子，因此溢流目标必然在后结算，溢流链也与时序无关。
4. **每池台账恒等式**：`起始 + 来水 + 溢入 + 进水口 − 出水口 − 外排 − 溢流 = 留池`。
   地图与“上一回合台账”都使用这份数据。
5. **判定顺序**：先看检修格是否超过安全线（被淹即失败），再看目标是否达成，最后看回合是否用尽。
   目标达成即通关，当天不再推进。

结算只读取按“高程 + id”整理过的结构，原始数组里的支路排列不参与计算，
测试会显式地把关卡数组顺序反转后比对结果完全相等。

## 记录与复核

导出的记录（`waterway-drill/record@1`）包含每一回合确认的闸门、各池水量、各边通过量、
各池溢流量、逐池台账、胜负与失败原因，外加关卡 id 与**内容指纹**。

导入时 `replayRecord` 会：

- 拒绝不同 `schema`、不同 `levelId`、不同指纹（同名但被改过、或根本是别的关卡）的记录；
- 拒绝超出关卡回合上限、回合号不连续、含未知闸门的记录；
- 用当前关卡**从头重新结算**每一回合，再与记录逐字段比对（水量、通过量、溢流、台账、胜负、失败原因），
  任何差异都视为篡改或与关卡不符并明确报错。

指纹只覆盖影响结算的内容（池子容量/初始值/高程/来水/外排/溢流目标、闸门初始状态、
支路容量与端点、回合数与目标），**绘制坐标变化不会导致旧记录被拒**。

```

│   ├── view.ts           会话视图与回放视图共享的构建逻辑
│   ├── replay.ts         记录解析、逐字段复核、跨关卡拒绝
│   ├── solver.ts         穷举求解器（开发/测试用，证明关卡可解且不依赖随机）
│   ├── levels/index.ts   两个自制样例关卡
│   ├── browser.ts        浏览器入口（聚合导出）
│   └── ui/               画布场景工具与绘制
├── demo/                 浏览器演示（index.html + main.js + styles.css）
├── scripts/solve.ts      交叉检查关卡设计的命令行求解器
├── tests/                node:test 测试（核心、回放、渲染、页面接线）
└── package.json / tsconfig*.json
```

## 两个样例关卡

**一 · 争水的蓄水池**（3 回合）：泉眼与上游湖同时向中游蓄水池供水，蓄水池容量 12、
溢流会倒进安全线只有 3 的检修格 M。目标池 3 回合内要到 18。只靠泉眼来不及，
必须动用湖，但又得赶在蓄水池溢流淹检修格之前收闸——这是“争用同一池子”的核心。

**二 · 刚好到溢流线**（6 回合）：目标池容量与通关要求都恰好是 10，多一格就溢流进安全线为 0 的检修格 N
（哪怕 1 格也判负），少一格又达不到目标；水流要过三跳才能抵达，分叉井按容量比例分配。
全开闸门会让目标池冲过 10 而失败，必须逐步收闸停在溢流线上——这是“刚好到达溢流线”的核心。

两关都由 `scripts/solve.ts` 穷举验证存在确定通关走法，且全开闸门的确会失败；
测试也覆盖这两点，不依赖随机生成。

## 运行

需要 Node.js 20+（demo 测试用到 jsdom 与 @napi-rs/canvas，仅开发依赖）。

```sh
cd waterway-drill
npm install          # 安装 devDependencies
npm run typecheck    # 严格 TypeScript 类型检查
npm test             # 跑全部测试（node --test）
npm run build        # 把 src 编译到 build/（demo 需要）
npm run demo         # 启动静态服务器（端口 4173），浏览 http://localhost:4173/demo/
```

`npm run demo` 用的是仓库自带的 `renderer/` 同款静态服务器方式。demo 必须能同时访问
`demo/` 与 `build/`，因此请从 `waterway-drill/` 目录启动。

## 已知取舍

- 结算语义是规则设计（回合开始时规划出流、按高程顺序应用），不是物理管网仿真；
  它牺牲一点“同回合接力输水”的直觉，换取完全可复现、可对账、与文件顺序无关。
- 检修格判定在**当回合结束时**立即生效，不做“下一回合才淹”的延迟。
- 记录只保存走法与其派生结果；关卡内容用指纹绑定，而不是把整份关卡嵌入记录。
